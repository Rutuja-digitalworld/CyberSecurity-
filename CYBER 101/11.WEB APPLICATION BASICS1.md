# TASK 1:Web Application Components

## 1. Front End

* The **Front End** can be considered similar to the **surface of the planet**, the parts that an astronaut can see and interact with based on the laws of nature.
* A web application would have a user interact with it and use a number of technologies such as **HTML, CSS, and JavaScript** to do this.

### 1.1 HTML — Hypertext Markup Language

* **HTML** (Hypertext Markup Language) is a foundational aspect of web applications.
* It is a set of instructions or code that instructs a web browser on **what to display and how to display it**.
* It could be compared to simple organisms living on the planet; these organisms have **DNA**, which is the instructions for how simple organisms are put together.

### 1.2 CSS — Cascading Style Sheets

* **CSS** (Cascading Style Sheets) in web applications describes a **standard appearance**, such as:

  * Certain colours
  * Types of text<img width="291" height="462" alt="image (46)" src="https://github.com/user-attachments/assets/abc248c7-54ea-4f40-87c9-47b7ca95a4af" />

  * Layouts
* Continuing the analogy with DNA, these could be compared to the parts of DNA that describe the **colour, shape, size, and texture** of the simple organism.

### 1.3 JS — JavaScript

* **JS** (JavaScript) is part of a web application front end that enables **more complex activity in the web browser**.
* Whereas HTML can be considered a simple set of instructions on what to display, JavaScript is a more advanced set of instructions that allows **choices and decisions to be made on what to display**.
* In the planet analogy, JavaScript can be considered the **brain of an advanced organism**, which allows decisions to be made based on what and how something interacts with it.

# TASK2: Uniform Resource Locator (URL)

**Definition:** A URL is a web address that lets you access online content such as webpages, videos, photos, or other media.

---

## Anatomy of a URL

**Definition:** A URL consists of several parts, each playing a different role in helping you find and access the right resource.
<img width="1172" height="307" alt="image" src="https://github.com/user-attachments/assets/7586ede2-5a28-4818-96fe-5be17ab4521f" />

### Scheme

**Definition:** The scheme is the protocol used to access a website, such as HTTP or HTTPS.

### User

**Definition:** The user contains login details, usually a username, used to access resources requiring authentication.

### Host/Domain

**Definition:** The host or domain identifies the website being accessed and must be unique.

### Port

**Definition:** The port number directs the browser to the correct service on the web server, commonly 80 for HTTP and 443 for HTTPS.

### Path

**Definition:** The path points to the specific file or page on the server that you want to access.

### Query String

**Definition:** The query string starts with `?` and is used to pass information such as search terms or form inputs.

### Fragment

**Definition:** The fragment starts with `#` and points to a specific section of a webpage.

# TASK 3: HTTP MESSAGES
# 🌐 HTTP Messages

HTTP messages are **data packets exchanged between a Client (Browser) and a Web Server**.

They allow the client and server to **communicate with each other**.

---

## 🔄 Types of HTTP Messages

| Type                 | Sent By         | Purpose                         |
| -------------------- | --------------- | ------------------------------- |
| 📤 **HTTP Request**  | Client → Server | Requests an action/resource     |
| 📥 **HTTP Response** | Server → Client | Sends the result of the request |

---

## 🧩 Structure of an HTTP Message

```text
┌──────────────────┐
│   Start Line     │
├──────────────────┤
│     Headers      │
├──────────────────┤
│   Empty Line     │
├──────────────────┤
│      Body        │
└──────────────────┘
```

### 1️⃣ Start Line

The **first line** of the message.

* **Request:** Contains HTTP method + URL/path
* **Response:** Contains HTTP version + status code

**Example:**

```text
GET /login HTTP/1.1
HTTP/1.1 200 OK
```

---

### 2️⃣ Headers 🏷️

Headers are **key-value pairs** that provide additional information about the request or response.

**Examples:**

```text
Host: example.com
Content-Type: application/json
User-Agent: Mozilla/5.0
```

They can provide information about **content type, security, cookies, browser, server**, etc.

---

### 3️⃣ Empty Line ↔️

An **empty line separates the headers from the body**.

```text
Headers
Headers
Headers

Body
```

---

### 4️⃣ Body 📦

The body contains the **actual data/content**.

* **Request Body:** Data sent by the client, e.g. login credentials or form data.
* **Response Body:** Data returned by the server, e.g. webpage or API data.

---

## 🔐 Why Learn HTTP Messages?

Understanding HTTP messages helps you:

* 🌐 Understand how websites communicate
* 🛠️ Troubleshoot web communication issues
* 🔍 Analyze requests and responses
* 🛡️ Understand web security
* 🚨 Identify potential vulnerabilities

---

## 🎯 Quick Answers

> **Q1. Which HTTP message is returned by the web server after processing a client's request?**

✅ **HTTP Response**

> **Q2. What follows the headers in an HTTP message?**

✅ **An Empty Line, followed by the Body**

# TASK4:-📤 HTTP Requests: REQUEST LINE AND METHODS

An **HTTP Request** is a message sent by the **Client → Web Server** to request a resource or perform an action.

```text
👤 Client
   │
   │  HTTP Request
   ▼
🌐 Web Server
```

---

## 🧩 HTTP Request Structure

```text
METHOD /path HTTP/version
Headers
Headers

Body
```

### 📌 Example

```http
GET /login HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
```

---

## 1️⃣ Request Line

The **Request Line** is the first line of an HTTP request.

It contains **3 parts**:
<img width="861" height="443" alt="image (51)" src="https://github.com/user-attachments/assets/6518ac6c-19b7-4a5b-89ea-1ddb8ce33d78" />

```text
GET   /login   HTTP/1.1
 ↓       ↓         ↓
Method  Path    Version
```

---

## 2️⃣ HTTP Methods 🛠️

HTTP methods tell the server **what action the client wants to perform**.

| Method         | Purpose                     | 🔐 Security Note                 |
| -------------- | --------------------------- | -------------------------------- |
| 🟢 **GET**     | Fetch data                  | Don't expose sensitive data      |
| 🔵 **POST**    | Send/create data            | Validate input against SQLi/XSS  |
| 🟡 **PUT**     | Replace/update resource     | Check authorization              |
| 🔴 **DELETE**  | Delete resource             | Allow only authorized users      |
| 🟣 **PATCH**   | Partially update resource   | Validate input                   |
| ⚪ **HEAD**     | Get headers only            | Similar to GET, without body     |
| 🟠 **OPTIONS** | Shows supported methods     | Disable if unnecessary           |
| 🟤 **TRACE**   | Used for debugging          | Often disabled for security      |
| 🔷 **CONNECT** | Creates a tunnel/connection | Commonly used with HTTPS proxies |


---

## 3️⃣ URL Path 🔗

The **URL Path** identifies the specific **resource or endpoint** the client wants.

Example:

```text
https://tryhackme.com/api/users/123
                    └─────────────┘
                       URL Path
```

Here:

```text
/api/users/123
```

identifies a specific user/resource.

### 🔐 Security

Always:

* ✅ Validate the path
* ✅ Prevent unauthorized access
* ✅ Sanitize input
* ✅ Protect sensitive resources

---

## 4️⃣ HTTP Version 🌐

The HTTP version tells the client and server **which version of the HTTP protocol they are using**.

| Version        | Year | Key Feature                               |
| -------------- | ---: | ----------------------------------------- |
| **HTTP/0.9**   | 1991 | Basic GET                                 |
| **HTTP/1.0**   | 1996 | Headers + better content support          |
| ⭐ **HTTP/1.1** | 1997 | Persistent connections + chunked transfer |
| 🚀 **HTTP/2**  | 2015 | Multiplexing + header compression         |
| ⚡ **HTTP/3**   | 2022 | Uses QUIC for faster communication        |

### ⭐ Most Important

**HTTP/1.1** became widely adopted and is known for:

* 🔗 Persistent connections
* 📦 Chunked transfer encoding
* 🗂️ Better caching

# TASK 5:🏷️ HTTP Request Headers & Body

HTTP Requests contain **Headers** and sometimes a **Body** to provide information to the web server.

```text
📤 HTTP Request
      │
      ├── 📝 Request Line
      ├── 🏷️ Headers
      │
      ├── ↔️ Empty Line
      │
      └── 📦 Body
```

---

# 🏷️ Request Headers

**Request Headers** provide additional information about the request and tell the server **how to process it**.

### 🔑 Common Request Headers

| Header              | Example                          | Purpose                                                |
| ------------------- | -------------------------------- | ------------------------------------------------------ |
| 🌐 **Host**         | `Host: tryhackme.com`            | Specifies the **domain/server** the request is sent to |
| 🖥️ **User-Agent**  | `User-Agent: Mozilla/5.0`        | Identifies the **browser/client**                      |
| 🔗 **Referer**      | `Referer: https://google.com/`   | Shows where the request **came from**                  |
| 🍪 **Cookie**       | `Cookie: user_type=student`      | Sends previously stored **cookie data**                |
| 📦 **Content-Type** | `Content-Type: application/json` | Specifies the **format of the request body**           |

### 🧠 Easy Memory

```text
Host        → 🌐 Where?
User-Agent  → 🖥️ Who/Which browser?
Referer     → 🔗 From where?
Cookie      → 🍪 Stored data
Content-Type → 📦 What format?
```

---

# 📦 Request Body

The **Request Body** contains the actual data sent from the client to the server.

It is commonly used with:

**POST, PUT, PATCH**

Example:

```http
POST /profile HTTP/1.1
Host: tryhackme.com
Content-Type: application/x-www-form-urlencoded

name=Alex&age=27
```

---

# 🧩 Common Request Body Formats

## 1️⃣ URL Encoded

**Content-Type:**

```text
application/x-www-form-urlencoded
```

Data is sent as **key=value pairs** separated by `&`.

```text
name=Alex&age=27&country=US
```

### ⭐ Remember

`key=value&key=value`

---

## 2️⃣ Form Data

**Content-Type:**

```text
multipart/form-data
```

Used when sending **multiple data parts**, especially **file uploads**.

```text
username → Alex
profile_pic → alex.jpg
```

📌 Commonly used for **image/file uploads**.

---

## 3️⃣ JSON

**Content-Type:**

```text
application/json
```

Data is represented using **name : value** pairs inside `{ }`.

```json
{
  "name": "Alex",
  "age": 27,
  "country": "US"
}
```

📌 Very common in **APIs**.

---

## 4️⃣ XML

**Content-Type:**

```text
application/xml
```

Data is stored using **opening and closing tags**.

```xml
<user>
    <name>Alex</name>
    <age>27</age>
    <country>US</country>
</user>
```

---

# ⚡ Quick Comparison

| Format          | Content-Type                        | Common Use         |
| --------------- | ----------------------------------- | ------------------ |
| **URL Encoded** | `application/x-www-form-urlencoded` | Simple form data   |
| **Form Data**   | `multipart/form-data`               | File/image uploads |
| **JSON**        | `application/json`                  | APIs               |
| **XML**         | `application/xml`                   | Structured data    |
