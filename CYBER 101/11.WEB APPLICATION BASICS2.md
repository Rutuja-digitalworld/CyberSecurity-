## 1. Status Line

The Status Line is the first line of an HTTP response. It contains three parts:

```http
HTTP/1.1 200 OK
```

| Part     | Meaning       |
| -------- | ------------- |
| HTTP/1.1 | HTTP version  |
| 200      | Status code   |
| OK       | Reason phrase |

                    STATUS LINE
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
      HTTP VERSION   STATUS CODE   REASON PHRASE
             │           │           │
             ▼           ▼           ▼
          HTTP/1.1       200          OK
             │           │           │
             ▼           ▼           ▼
        HTTP version   Request      Short human-
                       result       readable meaning

### Q1. Which part provides the HTTP version, status code, and brief explanation?

**Answer: Status Line**

## 2. HTTP Status Code Categories

| Status code | Category      | Meaning                                     |
| ----------- | ------------- | ------------------------------------------- |
| 100–199     | Informational | Request is being processed.                 |
| 200–299     | Successful    | Request succeeded.                          |
| 300–399     | Redirection   | Resource moved or another action is needed. |
| 400–499     | Client Error  | Problem with the client's request.          |
| 500–599     | Server Error  | Problem on the web server.                  |

### Q2. Which category indicates an internal server issue?

**Answer: 500–599 (Server Error Responses)**

# TASK 7:🌐 HTTP Response- Headers And Body

When a web server responds to an HTTP request, it sends **HTTP Response Headers**.

These headers are **key-value pairs** that provide important information about the response and tell the client (usually the browser) **how to handle it**.

### 📌 Example
<img width="953" height="591" alt="image (53)" src="https://github.com/user-attachments/assets/93b1c037-f617-492b-844d-cd00bc0fd308" />

```http
Content-Type: text/html
Content-Length: 1024
Date: Fri, 23 Aug 2024 10:43:21 GMT
```

### 🔄 Basic Flow

```text
HTTP Request
     │
     ▼
┌───────────────┐
│  Web Server   │
└───────┬───────┘
        │
        ▼
 HTTP Response
        │
   ┌────┴────┐
   ▼         ▼
Headers     Body
   │         │
   │         └── HTML / JSON / Images
   │
   └── Information + Instructions
```

---

# 📋 1. Required Response Headers

These headers provide important information required to process the HTTP response correctly.

| Header            | Purpose                                  |
| ----------------- | ---------------------------------------- |
| 📅 `Date`         | Shows when the response was generated    |
| 📄 `Content-Type` | Tells what type of content is being sent |
| 🖥️ `Server`      | Shows the web server software            |

---

## 📅 Date

```http
Date: Fri, 23 Aug 2024 10:43:21 GMT
```

* Shows the **exact date and time** when the server generated the response.

---

## 📄 Content-Type

```http
Content-Type: text/html; charset=utf-8
```

Tells the client **what type of content** it is receiving.

### Examples

```text
text/html           → HTML page
application/json    → JSON data
image/png           → PNG image
```

`charset=utf-8` specifies the **character encoding** used to display the content correctly.

---

## 🖥️ Server

```http
Server: nginx
```

* Shows the **web server software** handling the request.
* Useful for **debugging**.
* ⚠️ It may reveal information about the server that attackers could use.
* Because of this, websites may **hide or remove** this header.

> 🔐 **Security Point:**
> Server information disclosure can help attackers identify potential targets or vulnerabilities.

---

# 🍪 2. Other Common Response Headers

These headers provide additional instructions to the browser/client.

---

## 🍪 Set-Cookie

```http
Set-Cookie: sessionId=38af1337es7a8
```

Used by the server to send a **cookie** to the client.

### 🔄 Cookie Flow

```text
Server
  │
  │ Set-Cookie
  ▼
Browser
  │
  │ Stores Cookie
  ▼
Future Requests
  │
  └──────► Cookie sent back to Server
```

### 🔐 Important Cookie Flags

| Flag          | Purpose                                       |
| ------------- | --------------------------------------------- |
| 🔒 `Secure`   | Cookie is sent only over HTTPS                |
| 🚫 `HttpOnly` | Prevents JavaScript from accessing the cookie |

### Secure

```http
Set-Cookie: sessionId=abc123; Secure
```

* Cookie is transmitted only over **HTTPS**.
* Protects it from being exposed through unencrypted HTTP connections.

### HttpOnly

```http
Set-Cookie: sessionId=abc123; HttpOnly
```

* Prevents JavaScript from accessing the cookie.
* Helps reduce the risk of **XSS (Cross-Site Scripting)** attacks stealing cookies.

---

# 🗄️ Cache-Control

```http
Cache-Control: max-age=600
```

Controls how long the browser can **cache** the response.

### Example

```text
max-age=600
      │
      ▼
Cache for 600 seconds
```

For sensitive information, caching can be restricted using directives such as:

```http
Cache-Control: no-cache
```

---

# 📍 Location

```http
Location: /index.html
```

* Mainly used with **3xx Redirection** responses.
* Tells the client where to go next.

### 🔄 Redirection Flow

```text
Client
  │
  │ Request
  ▼
Server
  │
  │ 3xx + Location
  ▼
New URL
```

⚠️ If attackers can control the redirect destination and it is not properly validated, it can lead to an:

**Open Redirect Vulnerability**

---

# 📦 3. Response Body

The **HTTP Response Body** contains the actual data sent by the server.

### Examples

```text
🌐 HTML
📋 JSON
🖼️ Images
📁 Files
```

Example:

```html
<h1>Hello World</h1>
```

### 🛡️ Security

User-generated data should be properly **sanitised and escaped** before being included in the response.

This helps prevent injection attacks such as:

```text
XSS
│
└── Cross-Site Scripting
```

# 🔒 1. Content-Security-Policy (CSP)

**CSP** provides an additional security layer that helps protect against attacks such as **XSS (Cross-Site Scripting)**.

It allows website administrators to specify **which domains or sources are trusted** for different types of content.

### 📌 Example

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.tryhackme.com; style-src 'self'
```

### 🧩 Important CSP Directives

| Directive     | Purpose                                          |
| ------------- | ------------------------------------------------ |
| `default-src` | Defines the default allowed source               |
| `script-src`  | Defines where JavaScript can be loaded from      |
| `style-src`   | Defines where CSS stylesheets can be loaded from |

### ⭐ What does `'self'` mean?

```text
'self'
  ↓
Same domain where the website is hosted
```

---

### 🔍 Breaking Down the Example

```http
default-src 'self';
```

➡️ By default, content can only come from the **current website**.

```http
script-src 'self' https://cdn.tryhackme.com;
```

➡️ Scripts can be loaded from:

* The current website
* `https://cdn.tryhackme.com`

```http
style-src 'self'
```

➡️ CSS stylesheets can only be loaded from the **current website**.

### 🛡️ CSP Flow

```text
Website requests a resource
            │
            ▼
      CSP checks source
            │
       ┌────┴────┐
       ▼         ▼
    Allowed    Blocked
       │         │
       ▼         ▼
   Resource    Resource
    loads       denied
```

---

# 🔐 2. Strict-Transport-Security (HSTS)

**HSTS** ensures that web browsers connect to the website using **HTTPS**.

### 📌 Example

```http
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
```

### 🧩 HSTS Directives

| Directive           | Purpose                                    |
| ------------------- | ------------------------------------------ |
| `max-age`           | Time in seconds for which HSTS is enforced |
| `includeSubDomains` | Applies HSTS to all subdomains             |
| `preload`           | Allows inclusion in browser preload lists  |

---

## ⏳ max-age

```text
max-age=63072000
       ↓
HSTS policy remains active
for 63,072,000 seconds
```

---

## 🌐 includeSubDomains

This directive applies the HTTPS requirement to **all subdomains**.

```text
example.com
    │
    ├── www.example.com
    ├── login.example.com
    └── api.example.com
           │
           ▼
     HTTPS required 🔒
```

---

## 🚀 preload

* Allows the website to be included in **HSTS preload lists**.
* Browsers can enforce HTTPS **before the user's first visit** to the website.

---

# 🧪 3. X-Content-Type-Options

This header prevents browsers from **guessing or sniffing** the MIME type of a resource.

### 📌 Example

```http
X-Content-Type-Options: nosniff
```

### `nosniff`

```text
Server specifies Content-Type
            │
            ▼
        Browser
            │
            ▼
Does NOT guess MIME type
            │
            ▼
Uses specified Content-Type
```

### 🛡️ Why is it useful?

It helps protect against **MIME type sniffing attacks**, where browsers may incorrectly interpret a resource as a different type.

---

# 🔗 4. Referrer-Policy

The **Referrer-Policy** header controls how much **referrer information** is sent to another website when a user navigates from one website to another.

### 📌 Common Policies

```http
Referrer-Policy: no-referrer
```

```http
Referrer-Policy: same-origin
```

```http
Referrer-Policy: strict-origin
```

```http
Referrer-Policy: strict-origin-when-cross-origin
```

---

## 🧩 Referrer-Policy Directives

| Policy                            | Meaning                                                                                   |
| --------------------------------- | ----------------------------------------------------------------------------------------- |
| `no-referrer`                     | Sends no referrer information                                                             |
| `same-origin`                     | Sends referrer only to the same origin                                                    |
| `strict-origin`                   | Sends only the origin when protocol remains the same                                      |
| `strict-origin-when-cross-origin` | Sends more information for same-origin requests and only origin for cross-origin requests |

---

### 🚫 no-referrer

```text
Website A ───────► Website B
             ❌
       No referrer sent
```

Completely prevents referrer information from being sent.

---

### 🏠 same-origin

```text
Same Website
     │
     └──► Referrer information sent ✅

External Website
     │
     └──► Referrer information NOT sent ❌
```

---

### 🔐 strict-origin

Only the **origin** is sent when the protocol remains the same.

```text
HTTPS → HTTPS
   │
   ▼
Origin sent ✅
```

---

### 🔒 strict-origin-when-cross-origin

* Same-origin requests can include more detailed referrer information.
* Cross-origin requests send only the **origin**.

```text
Same Origin
     │
     ▼
More referrer information

Cross Origin
     │
     ▼
Only origin
```
